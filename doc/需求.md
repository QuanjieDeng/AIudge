# AI代码审核后台系统 需求文档

## 1. 项目背景

当前SLG项目后端代码95%以上由AI生成,人工review存在覆盖不足、疲劳漏检的问题。AI生成代码存在一些典型隐患:逻辑边界case遗漏、重复造轮子、安全校验缺失(尤其是资源/战斗结算等核心数值逻辑)、性能陷阱(N+1查询、锁滥用)等。

需要建立一套"AI审AI"的代码复审后台系统,对每日代码提交进行自动化复审,并支持人工对复审结果进行标注、协作、统计分析,形成闭环管理。

### 1.1 现状数据(用于校准设计规模)

| 项 | 实测值 |
|---|---|
| 代码规模 | 6271 个 `.go` 文件 / 41万行(手写部分约 23 万行,排除 `*.pb.go` 与 Luban 表) |
| 提交量 | 近30天 294 个 commit(约 13 个/活跃日) |
| 代码变更量 | 约 3400 行手写 Go/天;**生成代码占全部变更约 45%** |
| 提交人 | 4~5 个真人 + 1 个 CI 机器人账号 |
| 技术栈 | Go / 自建框架,存储为 Redis + ES + etcd(无关系库) |
| 现有资产 | `golangci-lint`(已开10个linter)、`.claude/skills/go-convention/SKILL.md`、`CLAUDE.md` 硬约束、飞书机器人 webhook |
| 现有缺口 | 无 CI/CD 配置、无历史bug清单文档、无统一测试入口 |

## 2. 项目目标

- 降低人工review的重复劳动,让人工精力聚焦在AI标记的高风险问题上
- 沉淀代码问题数据,支持团队做质量趋势分析和流程改进
- 形成可追溯、可分发、可统计的代码质量管理闭环

## 3. 用户角色

| 角色 | 权限说明 |
|---|---|
| 管理员 | 仓库配置、模型配置、任务调度配置、账号权限管理 |
| 普通用户 | 查看全部报告、标注问题、评论、指派任务、导出报表、处理指派给自己的问题 |
| 项目管理员 | 项目内的仓库配置、成员与权限管理;默认拥有项目内全部权限 |
| 项目级权限(可分配) | 项目管理员在成员管理里逐项授予。首项为「手动触发审核」——它直接消耗模型额度, 所以不跟「看得见仓库」绑定(§4.1) |

- 团队规模为 4~5 人,原三级角色中的"审核负责人"职责并入"普通用户",不单独设角色。
- **登录方式:飞书扫码登录**。系统以飞书 `user_id` 作为用户唯一标识——§4.5 的指派通知需要在飞书上 @ 到具体人,该映射由登录流程自然建立,无需另外维护。

## 4. 功能需求

### 4.1 仓库管理模块

- 支持新增/编辑/删除仓库配置,字段包括:仓库名称、Git地址、分支、访问凭据(建议只读token)、所属团队
- **路径过滤(新增)**:每个仓库可配置包含/排除 glob。默认排除 `autogen`、`*.pb.go`、`/tbl/`(与现有 `.golangci.yml` 保持一致)。生成代码占变更量约 45%,不排除会显著拉高成本并污染统计分布
- 支持为每个仓库挂载专属审核规范/checklist文档(编码规范、SLG业务重点关注项、历史bug清单),作为AI审核的上下文输入
  - 现状:编码规范与业务约束已有现成文档(`.claude/skills/go-convention/SKILL.md`、`CLAUDE.md`),可直接挂载
  - **历史bug清单当前无现成文档,第一版留空**(见 §8)
- 支持配置触发方式:
  - **Webhook触发(主)**:commit/PR提交时增量触发,反馈最快
  - **定时触发(兜底)**:可配置cron表达式(如每日22:00),**仅扫描过去24小时内未被webhook成功覆盖的commit**(网络故障、GitLab重试失败、直接推分支等)。需记录"已审核commit"清单以判定覆盖
  - **手动触发**:指定commit范围(下拉选提交,起始那一端不含)或时间范围(按提交时间筛,两端可留空)。
    提交候选每次打开下拉时先同步一次远端(只fetch,不动工作副本,避免与正在跑的任务抢工作区)。
    单次最多 30 条提交,与其余触发方式同一口径。
    手动触发会真实消耗模型额度,所以**按人授权**:项目管理员默认可用,其他成员需在成员管理里
    被授予「手动触发审核」权限(见 §3)
- 支持启用/禁用某个仓库的审核任务
- 访问凭据加密存储(见 §5)

### 4.2 模型配置模块

**复用内网 LiteLLM 网关,系统不直连各家模型API。**

- 配置网关地址、网关密钥、超时时间
- 模型列表从网关的 `/models` 接口拉取
- 支持设置默认模型
- 支持按仓库或按任务单独指定使用的模型(即模型名)
- 支持查看各模型的调用成本、响应时长等统计:**优先取网关自带计量能力**,网关未覆盖的指标再自行记录

> 因为网关已提供统一协议与计量,原需求中的"多模型适配层"不再需要(见 §5 可扩展性)。

### 4.3 任务调度与分发模块

- 任务队列管理,支持定时任务和webhook任务的异步执行
- 支持任务状态跟踪:排队中 / 执行中 / 成功 / 失败
- **失败重试**:最多重试 3 次,指数退避;仍失败则告警,不静默失败
- 支持并发数控制,避免同时触发过多任务导致API限流
- 任务执行日志留存,便于排查问题

### 4.4 报告查看模块

- 报告列表:按仓库、时间范围、严重等级、**来源**筛选查看历史报告
- 报告详情页:
  - 展示本次审核涉及的文件/commit列表
  - 每个问题项展示:文件路径、行号范围、严重等级、问题分类、**来源(AI模型 / golangci-lint)**、问题描述、AI建议的修复方案
    - 严重等级:**高危** / 建议 / 风格(风格级仅来自 lint)
    - 问题分类:安全 / 性能 / 逻辑 / 重复代码 / 规范(规范类仅来自 lint)
  - 支持关联到具体commit和提交人(提交人需经身份归并,见 §4.8)

> 严重等级原为"阻断/建议/风格"。**"阻断"改名为"高危"**:本系统只负责发现问题并分级,不阻断任何流程。要真正拦截 merge 需接入 GitLab blocking check,而仓库当前没有任何 CI 配置;且 §2 的目标是"让人看到"而非"把人卡住"。

### 4.5 标注与协作模块

- 每个问题项支持状态流转:待处理 → 已确认 → 已修复 / 误报
- **问题识别(新增)**:每条问题按 `(仓库 + 文件路径 + 问题分类 + 归一化代码片段)` 计算稳定指纹。指纹相同即视为同一问题,只更新行号等展示字段,不新建记录。行号不作为身份标识(插入/删除代码会导致行号漂移)
- **回归处理(新增)**:已标记为「已修复」或「误报」的问题,若其指纹在后续commit中再次出现,系统自动将其翻回「待处理」并标记「回归」,同时通知原指派人与提交人
- 支持对问题项添加评论,形成讨论串(支持多人协作)
- 支持将问题项指派给具体负责人,指派后通过飞书通知(见 §4.7)
- 支持批量操作:批量标记误报、批量指派

### 4.6 统计报表模块

- **趋势类**:周/月问题总量趋势图、按严重等级的堆叠趋势
- **分布类**:按仓库/子系统的问题分布、按问题分类(安全/性能/逻辑/重复代码/规范)的占比分布、按来源(AI / lint)的占比分布
  - 子系统维度直接复用 `.claude/doc/wiki/` 下已有的 20 个系统分类(战斗/公会/任务/英雄/商店/寻路/属性…)
- **效能类**:平均问题处理时长(**仅全局聚合,不按人拆分**)、问题处理率、误报率(用于评估AI审核质量,指导prompt优化)
- **人员类**:按负责人维度统计**处理数量**(不做处理时长,不做排名化展示)
- **版本标签(新增)**:每份报告记录 `模型名 / 模型版本 / prompt版本 / 规范文档版本` 四个标签。趋势图需据此标注断点——否则改变prompt或切换模型前后的数据不可比,曲线会失真且事后无法解释
- 支持报表按时间范围、仓库自由筛选导出

### 4.7 通知模块

- **渠道:仅飞书**,复用 `server/base/launch/alarm.go` 已有的 webhook 能力(原需求中的企业微信/邮件不做)
- **高危问题即时推送**:问题产生时立即推送,并 @ 指派人,附后台链接
- **每日汇总推送**:本次新增问题数、高危级问题数、待处理问题清单链接

### 4.8 审核口径与能力边界

| 问题分类 | 检测手段 | 说明 |
|---|---|---|
| 规范 / 风格 | **golangci-lint** | AI不参与。已有10个linter且为确定性判定,让LLM重复发现会浪费成本并污染误报率。lint的JSON输出解析后并入同一问题库与界面 |
| 逻辑 | AI(单文件) | 边界case、条件分支、返回值处理 |
| 安全 | AI + 代码库检索 | 校验缺失、越权、数值结算 |
| 性能 | AI + 代码库检索 | N+1查询、锁滥用需确认被调函数的实现,单文件审查看不见 |
| 重复代码 | AI + 代码库检索 | 判断"轮子是否已存在"必须先能查到已有实现 |

- **AI可调用代码库检索工具**,按需查询符号定义、已有实现与调用链,用于覆盖上表中的跨文件问题。不预先构建全量索引(代码每日变动,索引维护成本高),由AI按需检索。
- **提交人身份归并**:维护"同一人的多个git身份"映射表(如 `dengquanjie1` 与 `邓全杰` 为同一人);**机器人账号列入黑名单**(如 CI 账号),不计入任何统计。

### 4.9 界面与视觉

- **视觉方向:前卫、酷炫**。目标是做成团队内部工具里最不像"内部工具"的那一个。
- 两条硬边界:
  - **不牺牲扫描效率**:本系统最高频的使用场景是"每天扫一遍待处理列表"。视觉表现不得降低信息密度与扫读速度——酷炫体现在整体质感与数据可视化上,不体现在"关键信息要点开才能看到"上
  - **不阻塞首屏**:见 §5 前端性能
- 具体视觉规范(配色、字阶、组件库、动效曲线)另立设计文档,不在本需求文档展开

## 5. 非功能需求

- **安全性**:仓库访问凭据、模型API密钥需加密存储,不可明文展示。具体方案:通过环境变量或 k8s Secret 注入,不落配置文件明文,界面不回显,日志不打印
- **性能**:单次审核任务软超时 10 分钟(触发告警)、硬超时 30 分钟(终止并标记失败);正常任务 p95 < 10 分钟
- **前端性能**:问题列表与趋势图首屏渲染 < 1 秒;动效不得阻塞点击与滚动
- **可扩展性**:审核规则与 prompt 需可配置且带版本号(供 §4.6 的版本标签使用);模型接入依赖网关,无需自建适配层
- **可追溯性**:所有问题状态变更、评论、指派记录需保留操作人和时间戳,并支持查询操作审计日志

## 6. 核心数据实体(概述)

| 实体 | 关键字段 |
|---|---|
| repositories | 仓库配置、访问凭据(加密)、路径过滤 glob |
| review_tasks | 触发方式、状态、重试次数、**模型名/模型版本/prompt版本/规范文档版本** |
| task_logs | 任务执行日志(新增,§4.3要求留存) |
| review_reports | 关联任务、涉及文件/commit列表 |
| issues | **指纹**、来源(AI/lint)、分类、严重等级、状态、文件路径、行号、关联commit、指派对象 |
| comments | 问题项、内容、操作人、时间戳 |
| model_configs | 网关地址、网关密钥(加密)、模型列表、默认模型 |
| users | 飞书 user_id(登录标识) |
| committer_identities | git身份 → 人 / 机器人标记(新增) |
| audit_logs | 操作人、时间戳、变更内容(新增,§5可追溯性要求) |

## 7. 验收标准

- 可正常配置仓库并成功触发一次完整的审核任务,覆盖 webhook 触发与定时兜底两条路径
- 报告详情页可正常展示问题列表,并支持标注、评论、指派的完整操作闭环
- **回归检测可验证**:将一处已标记「已修复」的代码改动使其重新出现,系统能识别为同一问题、翻回「待处理」并标记「回归」
- **lint 结果并入**:golangci-lint 的输出可与AI问题一同展示在同一界面
- **统计报表可验证**:周维度趋势可正确生成;随机抽取 3 个报表数字,手工从问题库明细复算,结果一致
- **性能**:单次审核任务 p95 < 10 分钟
- 支持至少两种模型的切换配置,且切换对业务流程无影响

## 8. 待讨论/后续迭代方向

- 误报数据是否需要反哺到AI审核的prompt中,形成自优化闭环(系统需具备误报数据的导出能力)
- 历史bug清单的构建:第一版留空,待系统积累出带标注的真实问题数据后,再决定是否需要从 `doc/wiki/` 与 `doc/dev/*/03_闸门评审.md` 中挖掘归并
- 多仓库/跨项目扩展

> 原"待讨论"中的两项已在本轮评审中确定,移出本节:
> - "AI审核规则的版本管理" → 已由 §4.6 的版本标签解决
> - "是否与现有CI/CD流程打通" → 确定为**不做**,本系统只分级不拦流程(见 §4.4)

## 附录:本轮评审确定的决定

| # | 议题 | 决定 | 理由 |
|---|---|---|---|
| 1 | 问题项跨commit的身份 | 按代码内容计算稳定指纹,行号仅作展示 | 行号会因插入/删除代码而漂移,无法识别同一问题;否则趋势统计会变成"文件被改频率图" |
| 2 | 已关闭问题重现 | 自动翻回「待处理」+ 标「回归」 | "修了又回来"是AI生成代码最危险的情形,需要显式信号 |
| 3 | 严重等级"阻断"的效力 | 改名"高危",只分级不拦人 | 系统若真拦merge需接入GitLab blocking check,而仓库无任何CI配置;目标是减少漏检而非卡住流程 |
| 4 | 跨文件问题(重复造轮子/N+1) | 给AI检索工具,按需查代码库 | 这两类占§1核心痛点的半数,单文件审核根本看不见;预建索引维护成本高 |
| 5 | 定时与webhook触发的重叠 | webhook为主,定时仅兜底未覆盖的commit | 避免同一批代码被重复审核、报告列表出现重复报告 |
| 6 | prompt/模型变更后的可比性 | 报告打四个版本标签,趋势图标断点 | 优化prompt是本系统的既定动作,不打标签则历史曲线事后无法解释 |
| 7 | 存储选型 | 关系库,SQLite起步,需要时换Postgres | §6实体与§4.6的聚合需求是关系型负载,而现有技术栈只有Redis/ES/etcd;规模仅数千条/月 |
| 8 | 生成代码(占变更45%) | 仓库配置加路径过滤字段,默认抄`.golangci.yml` | 不排除会把上下文窗口和成本烧在噪音上,并污染分类分布 |
| 9 | 规范/风格类问题归属 | 交给golangci-lint,AI不报,输出并入同一界面 | lint是确定性判定且零成本;让LLM重复发现会虚高误报率,误导prompt优化方向 |
| 10 | 人员类统计 | 保留处理数量,去掉处理时长 | 5人团队中"处理时长"的信号被噪声淹没,且易被当作考核 |
| 11 | 与已有「闸门评审」流程的关系 | 并行,各管各的 | — |
| 12 | 通知渠道 | 仅飞书;高危即时推送+每日汇总 | 项目内只有飞书是通的;并行方案下,推送是保证有人看到的唯一机制 |
| 13 | 登录方式 | 飞书扫码 | 顺带建立§4.5所需的人员↔飞书user_id映射;§5的可追溯性也要求系统知道操作人身份 |
| 14 | 模型接入 | 复用内网LiteLLM网关,§4.2大幅缩水 | 网关已提供统一协议与计量,原"多模型适配层"不再需要 |
| 15 | 用户角色 | 三级降为两级(管理员/普通用户) | 4~5人团队,三级RBAC的权限矩阵永远只有三行 |
| 16 | 审核粒度 | 改动行所在函数 + 直接调用链 | 整个文件太贵且引入无关评论;纯diff行看不到函数签名与上下文 |
| 17 | 提交人身份 | 加身份归并表 + 机器人黑名单 | 同一人存在两个git身份会被拆成两行;CI账号30天提交70次会污染统计 |
| 18 | 历史bug清单 | 第一版留空,改为可选挂载 | 仓库内无现成文档,人工挖掘投入产出比低;系统跑起来后的标注数据是更干净的来源 |
